# Отклонения от контракта

Контракт этапа 1 лежит у владельца (личный дизайн-док, в репо не коммитится). Здесь перечислено, где реализация отличается от него и почему.

| Пункт контракта | Что сделано вместо | Почему |
| --- | --- | --- |
| §5 `Transport::prepare` «сбрасывает всё» | Сбрасывает позицию и останавливает транспорт, но BPM сохраняет | `prepare()` вызывается при каждой смене устройства или буфера. Полный сброс вернул бы 172 BPM, пока UI показывает другое значение. |
| §3 `JUCE_DISPLAY_SPLASH_SCREEN=0` | Флаг не задаётся | JUCE 8.0.14 его игнорирует и печатает предупреждение на каждую сборку. |
| §6 `JackalLookAndFeel::getTypefaceForFont` (Consolas) | Consolas берётся, только если шрифт реально найден; иначе дефолтный | Без Consolas (не Windows) JUCE отдавал пустой шрифт и текст не рисовался вообще. На Windows поведение то же, что в контракте. |

Не отклонения, а уточнения деталей, которые контракт не задавал:

- Клик метронома начинается с ненулевого сэмпла (огибающая атаки считается от i + 1, осциллятор в косинусной фазе). Так начало клика попадает ровно в сэмпл доли, что нужно для T1.
- `EngineCore` сбрасывает метроном на командах Play/Stop, чтобы после повторного Play счёт долей шёл с нуля.
- Входной индикатор меряет выбранный канал входа (тот, что идёт в монитор), а не все входы сразу.
- Индекс канала входа считается среди активных каналов устройства: так их отдаёт аудиоколбэк JUCE.
- Grep-проверка из §7 п.1 в буквальном виде не может быть пустой: подстрока `lock` есть в словах `block`, `maxBlockSize`, `lock-free`. Проверка выполняется по целым словам: `grep -rnwE "new|malloc|mutex|lock|lock_guard|unique_lock|cout|printf" Source/Engine/` — пусто.
- CI и README не задают генератор `-G "Visual Studio 17 2022"`: на раннерах GitHub `windows-latest` теперь стоит VS 2026, и CMake с жёстким генератором 2022 не находил студию. Без `-G` CMake берёт самую новую установленную Visual Studio.

## Этап 2

| Пункт контракта | Что сделано вместо | Почему |
| --- | --- | --- |
| §5.1 команды | Добавлена `SetTrackFit` (ivalue = track \| fit << 8) | В контракте не было способа передать флаг подгонки под темп в движок. |
| §5.7 `Sequencer::process` / `liveHit` | Аргументы собраны в структуру `SequencerContext` | Длинный список аргументов, одна и та же структура нужна командам и MIDI в `EngineCore`. Семантика та же. |
| §5.6 `TrackPlayer::choke()` | `choke(offset)`: чоук ставится в очередь событий дорожки с офсетом и применяется в `render()` по порядку | Без офсета удар CH в середине блока глушил бы OH с начала блока. |
| §5.8 `GlitchProcessor::padUp(offset)` | `padUp(offset, pad)` | «padUp действует только на активный пэд»: для этого нужен номер пэда. |
| §5.6 атака голоса 32 сэмпла | Атака `(i + 1) / 32`, первый сэмпл удара не нулевой; в `TriggerParams` есть `attackSamples`, движок всегда ставит 32 | V1 (побитовое чтение слайса) проверяется на уровне `Voice` с атакой 0 и паном -1 (усиление левого канала ровно 1). R2 сравнивает отношения амплитуд ударов ролла. |
| §5.6 пан constant-power | При `pan = ±1` противоположный канал ровно 0 | `cos(π/2)` в double не равен нулю, и в «глухом» канале оставался шум 1e-17. |
| §5.7 пропущенный онсет «играет с офсетом 0» | Онсет, отставший больше чем на длину блока, пропускается молча | Иначе паттерн, пришедший с опозданием, проигрывал бы все прошлые шаги разом. Смена темпа отстаёт максимум на сэмпл, этот случай не изменился. |
| §5.7 смена скорости строки на играющем паттерне | `nextK` пересчитывается от текущей доли | Иначе шаг k после смены ×1 → ×2 оказывался бы далеко в прошлом или будущем. |
| §8.2 «сериализуются только активные шаги» | Плюс неактивные шаги, у которых есть метки (поле `"a": false`) | ПКМ стирает шаг, но сохраняет его ратчет, слайс и p-locks (§9.3). Без этого метки терялись бы при сохранении, и J1 не проходил. |
| §8.2 `std::expected` | `ParseResult { ok, unique_ptr<Project>, error }` | Разрешено контрактом. Проект лежит в куче: он весит около 200 КБ, на стеке MSVC это опасно. |
| §8.5 `makeDemoProject` | Строка BREAK длиной 32 шага (все активны) | Демо-брейк нарезан на 32 слайса на 2 такта. Строка из 16 шагов играла бы только первый такт брейка. |
| §8.5 `clap` | Длина 183 мс (4 всплеска по 11 мс + хвост 150 мс) | Длина в контракте не задана, D1 проверяет её по этому числу. |
| §8.6 транзиенты | Онсет засчитывается по фронту: детектор взводится, когда `env` опускается ниже порога | Без этого затухающий удар давал второй ложный онсет через 30 мс. |
| §9.3 ЛКМ по ячейке | Переключение происходит на отпускании, если мышь не ушла в соседнюю ячейку и не тянули по вертикали | Иначе протяжка громкости на активном шаге сначала выключала бы его. Кисть по строке и протяжка громкости работают как в таблице. |
| §9.3 двойной клик | Прослушивание через `TriggerTrack` с громкостью шага | Отдельной команды «сыграть шаг с параметрами» в §5.1 нет. |
| §10 | Хелперы офлайн-рига в `Tests/RigHelpers.h`, O1 в `MutationTests.cpp` | Косметика: разбиение файлов внутри папки. |

Ручная проверка на Windows, которую CI не делает: русская раскладка и клавиши `Q..K`, `Z..,` (JUCE отдаёт коды физических клавиш через виртуальные коды Windows; если на русской раскладке не сработает, записать сюда).

## Этап 3

| Пункт контракта | Что сделано вместо | Почему |
| --- | --- | --- |
| §5.9 п.2.1 p-lock «действует с начала отрезка, в котором стоит» | Действует с первой границы контрольного блока (32 сэмпла) в момент удара или после него | При буфере 7 начало контрольного блока уже сыграно в прошлом колбэке, «назад» применить нельзя. С правилом «на следующей границе» K4 побитово равен на буферах 7…1024. Опоздание не больше 31 сэмпла (0.65 мс), меньше атаки голоса. |
| §5.9 список p-lock-событий 128 | Очередь 128 событий хранит позицию потока, а не офсет | Нужна та же причина, что выше: событие из конца буфера применяется в следующем колбэке. |
| §7 п.3 `log`/`pow` только на границах блоков | μ-law в Bitcrush считает `log1p` и `pow` на каждом сэмпле | Формула §5.4 по-другому не считается. Аллокаций и блокировок нет; K6: девять полных цепей тратят 0.2 с на 10 с звука. |
| §4 «ParamTable инициализируется из ParamSpec» | Дефолты fx лежат в движке (`kFxParamDefaults` в `ParamIds.h`), `ParamSpec` берёт их оттуда | Движок не зависит от модели, как и в этапе 2. |
| §10 E2 `JACKAL_DISABLE_FX` | `EngineCore::setFxDisabledForTests (bool)` | Флаг без отдельной сборки. В приложении не вызывается. |
| §10 U1 монотонность `sp12FilterHz` | Монотонность проверяется, пока эффект включён | Нейтральное значение фильтра 10 кГц, а Iron включает SP-12 с 12 кГц. Значение выключенного эффекта на звук не влияет. |
| §10 K2 перестановка Crush ↔ Decim | Проверяется Crush ↔ Flip | Bitcrush поэлементный, Decimator это удержание: они коммутируют, и выход был бы равен. |
| §10 K3 «скачок между сэмплами ≤ 0.02 до клипа» | Окно от включения Drive (макро ≥ 0.55) до 0.8, граница 1/32 | До включения Drive скачки даёт сам SP-12 (фильтр стартует с нуля), после 0.8 Wrap и бит-флип. Между ними самый большой скачок это ступень Bitcrush 6 бит (1/32). |
| §10 K4 p-lock 1.0 даёт «клип 24 дБ» | p-lock 0.84 | Iron на 0.85 и выше переключает Drive в Wrap (таблица §5.8), клипа на 1.0 нет. 0.84 даёт 14.4 дБ Clip. Уровни сравниваются с учётом центрального пана (×0.707). |
| §10 K5 «после 1 с тишины выход ровно 0» с Iron 1.0 | Проверка при Iron 0.75 | На 1.0 включён бит-флип: он честно флипает бит и у нулевого сэмпла. |
